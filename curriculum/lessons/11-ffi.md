# Talking to C (FFI)

Almost every Rust project in automotive and embedded starts inside an
existing C (or C++) codebase: a vendor BSP, an RTOS, AUTOSAR basic software,
a decade of in-house libraries. Rust rarely replaces all of that. It slots in
as a component that C calls, and that calls C. Doing that safely is one of the
most valuable no_std skills you can bring to a team.

## The C ABI

`extern "C"` selects the platform's C calling convention, the contract for how
arguments, return values and registers are passed. Both sides must agree
exactly; the compiler can't check across the language boundary.

```rust
use core::ffi::{c_char, c_int, c_void};

// Rust function callable from C:  int32_t checksum(const uint8_t *data, size_t len);
#[unsafe(no_mangle)]                         // keep the symbol name "checksum"
pub extern "C" fn checksum(data: *const u8, len: usize) -> i32 { ... }
```

Type mapping rules of thumb:

| C | Rust |
|---|---|
| `int`, `unsigned`, `long`, `char` | `c_int`, `c_uint`, `c_long`, `c_char` (sizes vary by platform!) |
| `int32_t`, `uint8_t`, `size_t` | `i32`, `u8`, `usize` |
| `T *` / `const T *` | `*mut T` / `*const T` (never `&T` for pointers that may be NULL) |
| `void *` | `*mut c_void` |
| `struct S { ... }` | `#[repr(C)] struct S { ... }` |
| function pointer that may be NULL | `Option<unsafe extern "C" fn(...)>` (NULL ⇔ `None`, guaranteed) |
| `bool` (C99 `_Bool`) | `bool` |
| `enum` | prefer integer constants: a C enum value outside your Rust enum's range would be UB |

## Exporting a no_std library to C

Build the crate as a static library:

```toml
[lib]
crate-type = ["staticlib"]       # produces libname.a for the C linker
```

The C side links it like any other library and declares the functions in a
header, by hand or generated by **cbindgen**. Because a staticlib is a *final
artifact*, a no_std staticlib must define the `#[panic_handler]` (and the
allocator if it uses alloc). It must also be built with `panic = "abort"`.

### Never trust what crosses the boundary

C can pass anything: NULL, dangling pointers, wrong lengths, misaligned
storage. Your exported function is the **trust boundary**: validate what you
can, document what you can't, and turn raw parts into safe types once:

```rust
#[unsafe(no_mangle)]
pub extern "C" fn sum_u16(data: *const u16, len: usize, out: *mut u32) -> i32 {
    if data.is_null() || out.is_null() { return -1; }
    if !data.is_aligned() || !out.is_aligned() { return -1; }
    // SAFETY: non-null and aligned; the caller promises `len` readable elements
    // (documented in the header) and a writable `out`.
    let samples = unsafe { core::slice::from_raw_parts(data, len) };
    let total = samples.iter().map(|&s| u32::from(s)).fold(0u32, u32::wrapping_add);
    unsafe { out.write(total) };
    0
}
```

Conventions that keep C callers sane: return an `int` status (0 = OK,
negative = error kinds), write results through out-pointers, and never
return borrowed pointers whose lifetime C can't see.

### Opaque handles and caller-provided storage

C code often wants to own memory itself: static buffers, pools, the stack.
A common no-heap pattern: Rust exports the size and alignment of its private
type, C provides suitably sized storage, and Rust initialises the object in
place and hands back an *opaque* pointer:

```c
typedef struct Filter Filter;                 /* opaque: C never sees the fields */
extern const size_t NOSTD_FILTER_SIZE, NOSTD_FILTER_ALIGN;
Filter *nostd_filter_init(void *storage, size_t len, uint8_t window);
```

### Callbacks

C passes a function pointer plus a `void *user` context pointer, which Rust
passes back on each call:

```rust
pub type VisitFn = Option<unsafe extern "C" fn(user: *mut c_void, index: usize, value: i32)>;

#[unsafe(no_mangle)]
pub extern "C" fn for_each(f: *const Filter, cb: VisitFn, user: *mut c_void) -> i32 {
    let Some(cb) = cb else { return -1 };           // NULL function pointer
    // ... for each value: unsafe { cb(user, i, v) };
}
```

## Calling C from Rust

Declare foreign functions in an `unsafe extern` block (edition 2024). You can
mark individual items `safe` when calling them can never cause UB, like a
function with only integer arguments:

```rust
unsafe extern "C" {
    fn c_log(level: c_int, msg: *const c_char);   // unsafe to call: takes a pointer
    safe fn c_millis() -> u32;                      // safe to call
}

pub fn log(msg: &core::ffi::CStr) {
    // SAFETY: msg is a valid NUL-terminated string for the duration of the call.
    unsafe { c_log(1, msg.as_ptr()) }
}
```

C strings are NUL-terminated, Rust strings aren't. Use:

- `c"literal"` (Rust 1.77) for a `&'static CStr` literal;
- `CStr::from_bytes_until_nul(&buf)` to view a NUL-terminated buffer you filled;
- `CStr::from_ptr(p)` to wrap a pointer you received (it calls `strlen`);
- `alloc::ffi::CString` only if you have a heap.

For larger C APIs, **bindgen** generates the `extern` block from headers.

## Panics and unwinding across the boundary

Unwinding into C is undefined behaviour. Since Rust 1.81, a panic that would
escape an `extern "C"` function **aborts the process** instead. (Use
`extern "C-unwind"` if you deliberately want unwinding to pass through.) In
no_std with `panic = "abort"` there's no unwinding at all, but your exported
functions should still be panic-free: return error codes instead.

> software components running inside AUTOSAR Classic basic software on AURIX
